# Decisions

Small decisions made during the build, newest last. The handoff (`docs/handoff.md`) wins over the spec (`docs/spec-v1.2.md`); this file records what neither settles.

| # | Date | Decision | Why |
| --- | --- | --- | --- |
| 1 | 2026-11-11 | npm, not pnpm | The spec's commands are written for npm and Alex's AI will type them |
| 2 | 2026-11-11 | Default branch `main` | Convention |
| 3 | 2026-11-11 | Tailwind + daisyUI, not shadcn/ui | Handoff section 3. Unconfirmed by the principal; ask at gate 1 |
| 4 | 2026-11-11 | Browser tests of the dashboard use installed Chrome (`channel: "chrome"`), not a downloaded Chromium | GitHub's macOS runners ship Chrome, and the laptop has 8 GB free. Playwright's Chromium stays the fallback when Chrome is missing |
| 5 | 2026-11-11 | Chrome is installed by `npm run setup` with `brew install --cask google-chrome` when missing | Handoff section 8: install through setup |
| 6 | 2026-11-11 | Live pages are saved to `captures/` in the repo (git-ignored) and scrubbed into `fixtures/` before commit | Handoff section 4. Keeps real people's data out of git |
| 7 | 2026-11-11 | Domain terms live in `CONTEXT.md` | One vocabulary for code, UI and reports |
| 8 | 2026-11-11 | Selectors live per page in `src/linkedin/parse/selectors.*.ts`, plus `src/linkedin/selectors.ts` for the session | One file for every page would be edited by every parser slice at once |
| 9 | 2026-11-11 | Enumerations (stage, action type, job state) are TypeScript constants, not SQL CHECK constraints | Adding a value then needs no migration |
| 10 | 2026-11-11 | `session_state` is a single row (id 1) | One account, one dedicated window per install |
| 11 | 2026-11-11 | Page classification order: restriction wording, checkpoint URL, security-check wording, login wall, signed-in navigation, CAPTCHA markers, logged-out home, unknown | The login page and the signed-in messaging page both embed an invisible reCAPTCHA; both were first misread as checkpoints |
| 12 | 2026-11-11 | Saved pages are parsed with `node-html-parser`, not in the browser | Parsers are pure functions of the HTML, so fixtures test exactly what runs live |
| 13 | 2026-11-11 | Hand-written fixtures are named `synthetic-*` and are exempt from the leak guard's id rules | Their ids are invented; real captures keep the full guard |
| 14 | 2026-11-11 | The thread parser decides a sender from the profile link and the shown name, and throws when they disagree | A wrong sender would stop or continue a sequence wrongly; unreadable is safer than guessed |
| 15 | 2026-11-11 | No parser depends on `data-view-name` alone | LinkedIn writes it only into the first page a browser session loads; later loads have none (seen live) |
| 16 | 2026-11-11 | A conversation is opened by URL, `/messaging/compose/?recipient=<member id>`; the member id comes from Message links and is returned by `viewProfile` and `listRecentConnections` | No click and no second parser. Milestone 2 stores the member id on the person. See `docs/research/thread-navigation.md` |
| 17 | 2026-11-11 | `readThread` is for 1st-degree connections only | For anyone else the compose URL opens a new InMail form, which the parser refuses |
| 18 | 2026-11-11 | The driver latches on a login wall, checkpoint or restriction: every later call rethrows the same error without loading a page | A safety stop must not depend on every caller remembering to stop |
| 19 | 2026-11-11 | `live:check` prints counts only; full results go to `<data dir>/live-check/` | Real people's data stays out of terminals, logs and reports |
| 20 | 2026-11-11 | No review bot is installed on the repository. Each pull request is reviewed by the lead session and CI; `code-review` runs before each gate, `council` before gates 2 and 4 | The principal's brief. Pullfrog can be added if he asks |
| 21 | 2026-11-11 | Workers share one checkout and get disjoint files; the lead splits their work into pull requests | Per-agent worktrees were not available to this session |
| 22 | 2026-11-11 | Gate 1: the principal confirmed daisyUI, My Network → Grow as the recommendations page (profiles are opened for location, company and degree before scoring), and that agents merge their own pull requests once the work is tested | His answers at the gate |
| 23 | 2026-11-11 | Pullfrog reviews every pull request; its findings are fixed or answered before merge. Replaces decision 20 | The principal installed it at gate 1 |
| 24 | 2026-11-11 | The Italian `live:check` stays open | The principal had no answer at gate 1; switching the interface language is an account setting and needs his yes |
| 25 | 2026-11-11 | Due work is derived each tick from `prospects.stage` and `next_action_at`; recurring checks from the last ledger row of their type. The `jobs` table is dropped | One source of truth. A stored job could outlive a stop and send after a reply |
| 26 | 2026-11-11 | One ledger row per step per prospect (`invite:<id>`, `message1:<id>`, `followup:<id>`, `withdraw:<id>`). A send happens only after one transaction moves the row planned → in_progress, freezes the rendered text on the prospect and, for an invite, records the suppression | The database then refuses a second send of a step, whatever the code above it does |
| 27 | 2026-11-11 | Any throw from a send leaves the row `unknown`, never failed. Rows still `in_progress` when a tick starts become `unknown`. An unknown row is checked against LinkedIn before anything else happens to that prospect | The click may have happened. Sends are never blindly retried (spec section 6) |
| 28 | 2026-11-11 | A message of unknown result is judged by count: the claim stores how many of the user's messages the thread held. Same count → not sent, plan again. One more, and it is the text → sent. Anything else → needs review | LinkedIn may redraw the text (links, line breaks), so 'text not found' does not prove 'not sent' |
| 29 | 2026-11-11 | Before every message the thread is read: any message from the participant stops the sequence (replied); the user's own messages must be exactly the texts the app sent, in order, or the sequence stops (manual takeover). No thread polling between steps | Fails closed, and catches the user re-sending a template by hand. Replies after the follow-up are not tracked (handoff section 3) |
| 30 | 2026-11-11 | Suppression is on the person: `contacted_at` and `contacted_prospect_id`, set when the first invite is claimed and never cleared. The member id is required before an invite and unique across people; a person has at most one active prospect | A changed profile URL must not make a contacted person look new |
| 31 | 2026-11-11 | The profile is viewed right before an invite (ledger type `profile_view`, counted in that budget). Only `can_connect` or `connect_in_more` proceeds; pending, connected or anything else goes to needs review | Spec section 5. The view also supplies the member id |
| 32 | 2026-11-11 | An invite of unknown result whose profile now shows 1st degree goes to needs review, not accepted | The app cannot tell its own accepted invite from an earlier connection; a wrong guess sends a first message to someone who never got the invite |
| 33 | 2026-11-11 | Before withdrawing an old invitation the profile is viewed; 1st degree means the acceptance was missed and the prospect moves to accepted | An acceptance during long downtime can fall off the recent-connections page |
| 34 | 2026-11-11 | Safety stops have their own table and halt the whole engine until the user resumes. Campaign statuses are not rewritten. Three unexpected pages in a row are counted from ledger rows started after the last resume | `session_state` is overwritten by every session check. Counting from the resume stops an old streak from raising the stop again |
| 35 | 2026-11-11 | Budgets count every ledger row that was claimed, whatever its result. The invite warm-up allowance grows with the number of earlier calendar days that had an invite | LinkedIn saw the page load either way. Downtime must not advance the warm-up |
| 36 | 2026-11-11 | Withdrawals have a daily limit (`limits.withdrawalsPerDay`, default 10). Not in the spec | Without it, a return from two weeks off withdraws every expired invitation in one morning |
| 37 | 2026-11-11 | SQLite runs with `synchronous = FULL` and `fullfsync = ON` | A committed claim must survive a power cut, or the step is sent again |
| 38 | 2026-11-12 | An interrupted read (profile view, thread read, connections check) ends as failed with kind `interrupted`; only an interrupted send becomes unknown. It neither counts toward nor resets the unexpected-page streak | A read has nothing to reconcile. Found by the simulation: such rows stayed unknown for ever |
| 39 | 2026-11-12 | A restarted engine that finds a row left in progress waits one full random gap from the restart; otherwise from the newest ledger time | Found by the simulation: LinkedIn saw two page loads 41 s apart across a restart |
| 40 | 2026-11-12 | `{{first_name}}` comes only from the stored first name. With none stored the prospect is held for review; there is no fallback to the first word of the full name | 'Dott. Marco Rossi' must not be greeted as 'Dott.'. Milestone 3 fills first names |
| 41 | 2026-11-12 | At follow-up time the thread is read even when the campaign has no follow-up; a reply found there stops the sequence as replied, otherwise it completes | The Stats screen counts replies seen before the follow-up |
| 42 | 2026-11-12 | A sent follow-up closes the sequence as `completed` at once; the stage `follow_up_sent` is not used by the engine | Handoff section 3: the automation's job ends when the follow-up is sent |
| 43 | 2026-11-12 | Whoever runs the engine builds a new driver after a safety stop is resumed | A driver latches on a safety error (decision 18) |
| 44 | 2026-11-12 | The simulation closes the database connection to model a kill, and a separate test sends a real SIGKILL to a child process to prove a committed row survives and an uncommitted one does not | A real kill runs no catch handlers; closing the connection makes any handler in the engine harmless |
| 45 | 2026-11-12 | The working window is checked again, with fresh settings, right before every claim of a step | Council: a read that the laptop sleeps through could be followed by a send hours after closing time |
| 46 | 2026-11-12 | `sendMessage` carries how many messages the conversation showed when the engine judged it; the driver compares right before sending and sends nothing if it changed (`thread_changed`). On the real site the instant between that check and the click remains | Council: a reply landing between the thread read and the send was not seen, and the simulation forgave it. The forgiveness is removed |
| 47 | 2026-11-12 | An invite of unknown result is retried on 'Connect shown' only while its claim is under 14 days old; older goes to needs review | Council: an invitation the user withdrew by hand during a long downtime shows Connect again. LinkedIn blocks re-inviting for about three weeks, so 14 days is inside that |
| 48 | 2026-11-12 | A step is claimed at most 3 times; then the prospect goes to needs review | Council: a send that keeps failing before its effect was retried for ever, one thread read each time |
| 49 | 2026-11-12 | When the user pauses a campaign or changes a prospect's stage while the engine is working on it, the engine leaves the prospect as he set it and writes a log line. It never moves it to needs review for that, and never fails | Council: a pause during a read held the prospect for review; a reject during a read made the tick fail |
| 50 | 2026-11-12 | A message of unknown result counts as sent when the user's first new message in the conversation is that text, whatever he wrote after it. Refines decision 28 | Simulation: killed right after a send, then the user wrote by hand; the count rose by two and the prospect was held with the ledger row left unknown, although the message had gone out |
| 51 | 2026-11-12 | Known limit: the thread check accepts the invite note whether or not LinkedIn shows it in the conversation. If LinkedIn does not show it and the user types the identical text by hand, it is read as the note. Milestone 4 makes the rule exact once the live site shows which it is | Council. Cannot be settled without a real accepted invitation |
| 52 | 2026-11-12 | Known limit: a restart drops a scheduled long break and resets the break counter | Council. A restart is itself a pause; keeping break state across restarts adds stored state for little gain |
| 53 | 2026-11-12 | Withdrawals are picked after messages and before invites. There is no separate periodic session check: every driver call checks page health first and a safety error stops everything | The spec's priority list does not place withdrawals, and its 'health check' step is covered by the driver (decision 18) |
| 54 | 2026-11-12 | Only one process may run the engine. The app's port and the Chrome profile lock already stop a second app; milestone 3 must take both before the first tick and refuse to tick without them | Council: two engines on one database would each treat the other's in-progress send as interrupted and send it again. Not wired into `npm start` yet, so nothing can run twice today |
| 55 | 2026-11-12 | Every write operation takes a deadline (`notAfter`, the end of the working window). The driver reads the clock right before the effect and, if it is later, does nothing and answers `expired` | Council round 2: a laptop that sleeps inside the send call would click hours later |
| 56 | 2026-11-12 | Right before a claim the engine checks, with fresh settings: still inside the working window and not in its last 5 minutes, and the step's budget still open. It also loads the campaign and person again after a read, so a template edited during the read is the one used | Council round 2: a limit lowered or a template cleared during a read was ignored for that one action |
| 57 | 2026-11-12 | Breaks survive a restart: a new engine counts from the ledger how many pieces of work ran since the last pause of at least the minimum break, and carries on from there. Replaces decision 52 | Council round 2: a crash loop would never take a break |
| 58 | 2026-11-12 | A tick called while another is still running on the same engine does nothing | Council round 2: the second tick would treat the first one's in-progress send as interrupted and the step could go out twice |
| 59 | 2026-11-12 | A message of unknown result is 'not sent' only when the user's message count is unchanged and the text is nowhere in the conversation; unchanged count with the text present is 'unclear'. Refines decisions 28 and 50 | Council round 2: if LinkedIn shows the invite note before a send and not after, the count stays the same although the message went out |
| 60 | 2026-11-12 | LinkedIn's own refusals (its invitation limit, a conversation that changed, a deadline that passed) put the step back to planned without using one of its 3 attempts | Council round 2: nothing was tried, so nothing should count toward 'tried 3 times' |
| 61 | 2026-11-12 | An overdue invitation's profile check needs only the profile-view budget. If the invitation is still pending and the withdrawal budget is closed, it waits for that budget | Council round 2: with withdrawals set to 0, a missed acceptance was never found |
| 62 | 2026-11-12 | Known limit: working hours set inside the hour that repeats on the October clock change (02:00–03:00) can open up to an hour early on that one night. Daytime hours are not affected | Council round 2. Not worth a second time model for hours nobody sets |
| 63 | 2026-11-12 | The council review stopped after round 2 on the principal's instruction (diminishing returns). To check on the live site in milestone 4: whether LinkedIn shows the invite note in the conversation; how it redraws a message that contains a link; that re-inviting is blocked after a withdrawal (decision 47 relies on it) | The principal, 2026-11-12. The simulated LinkedIn cannot answer these |
